Pay via UPI — design

Date: 2026-10-21 · Status: Draft (brainstorm) — pending approval, then implementation plan · Author: Nanda + Claude

Intent

Settle-up today tells a household "Ravi pays Priya ₹1,240" and offers a "Settle up" button that only records the payment. In an Indian household the money itself moves over UPI (GPay, PhonePe, Paytm, BHIM…). This feature closes that gap: each member can store their UPI ID, and every suggested payment gets a Pay via UPI action that opens the payer's UPI app (on a phone) or shows a scannable QR code (on a laptop, or when paying from a different phone), with the payee and exact amount prefilled.

The app still cannot know whether a payment went through, so recording the settlement stays a deliberate second tap, exactly as it is today.

Goals

  1. Store an optional UPI ID per household member (works for attribution-only people who never sign in, e.g. a grandparent).
  2. On /settle-up, each suggested payment whose payee has a UPI ID gets a Pay via UPI button that opens a dialog with:
    • a QR code encoding the standard upi://pay link,
    • an "Open UPI app" link (<a href="upi://pay?…">) for phones,
    • the payee's name, UPI ID and the amount, so the payer can double-check,
    • a "Record payment" button that opens the existing record-settlement sheet prefilled with this suggestion (same as "Settle up").
  3. Zero integrations: no bank/UPI/PSP API, no webhooks, no secrets, nothing to verify. The deep link + QR are the whole mechanism.

Non-goals

  • Verifying or auto-recording payments. Recording stays manual.
  • Collecting money from people outside the household, or any public pay page.
  • Supporting currencies other than INR (UPI is INR-only; the feature hides itself when the household currency isn't INR).
  • Per-expense "pay this one" buttons; only the settle-up suggestions get it.
  • Reminders / nudges ("Ravi still owes you") — separate feature if wanted.
  • Carrying UPI IDs through CSV import/export.

Anti-goals (what would make this a failure)

  • A wrong amount or wrong payee in the prefilled UPI screen. The link must be built from validated, server-stored data only, with the amount formatted exactly (two decimals, no grouping).
  • A payer recording a settlement by accident because they tapped "Pay". Opening the link or QR must never write anything.
  • Cluttering the mobile settle-up row. The row keeps one primary action ("Settle up"); the UPI action is a compact secondary button.

Data model

household_members gains one nullable column:

upi_id TEXT NULL

Drizzle: upiId: text("upi_id"). Generate the migration with pnpm db:generate (next after 0009_careless_tenebrous). No backfill. No uniqueness constraint — two members legitimately can share one VPA (e.g. a couple with a joint handle).

Validation (src/lib/validators/member-schema.ts)

upiId is optional, like email: an empty string or absent field means "none" (store NULL). When present:

  • trim, then lowercase (VPAs are case-insensitive; storing lowercase keeps the QR/link deterministic);
  • must match ^[a-z0-9][a-z0-9._-]{0,254}@[a-z][a-z0-9]{1,63}$ (identifier: alphanumerics plus ., _, -; handle: letters/digits, e.g. okaxis, ybl, paytm, upi, axl); phone-number VPAs like 9876543210@ybl pass;
  • error message: "Enter a valid UPI ID, like name@bank".

createMember and updateMember read a upiId form field and persist it.

The UPI link (src/lib/upi.ts, pure, unit-tested)

buildUpiPayLink({ payeeVpa, payeeName, amount, note }): string

Produces the NPCI deep-link form, which is also exactly what a UPI QR encodes:

upi://pay?pa=<vpa>&pn=<name>&am=<amount>&cu=INR&tn=<note>

Rules:

  • am is the major-unit amount with exactly two decimals, no grouping (1240.00). Build it from the minor-unit integer (amountMinor), never from a float: ${Math.floor(m/100)}.${String(m%100).padStart(2,"0")}. The settle-up suggestions currently expose amount in major units; the builder may either add amountMinor to the suggestion shape or convert with Math.round(amount*100) at the boundary. Prefer the former.
  • pn is the payee's member name, trimmed to 50 characters.
  • tn is Outlay · <household name>, trimmed to 50 characters (several apps truncate or reject long notes). tn is informational only.
  • cu=INR always.
  • All values go through encodeURIComponent; spaces as %20, not +.
  • No tr/mc/tid fields (merchant-only).

UI

Members page (src/components/members/member-manager.tsx)

  • The add/edit member sheet gets a UPI ID (optional) input directly under Email: name="upiId", inputMode="email", autoCapitalize="none", placeholder name@bank, help text "Lets others pay this person with one tap from Settle up."
  • The member list shows the UPI ID under the email line, muted, when set.

Settle-up page (src/components/settle-up/settle-up-view.tsx)

  • participants already reach the view as { id, name }; extend to { id, name, upiId: string | null } (from getMembers). The page also passes householdName for the note.
  • Currency comes from useCurrency() (existing provider). When it is not "INR", render nothing UPI-related.
  • Each suggestion row: keep the current layout; add, left of "Settle up", a compact outline button with a QrCode lucide icon and the label Pay (icon-only at the narrowest widths, with aria-label="Pay via UPI"). Only when the payee (toId) has a upiId.
  • When the payee has no upiId, render the muted hint line below the row text with a link to /members.
  • Tapping Pay opens a Dialog (existing src/components/ui/dialog.tsx):
    • title: Pay {toName};
    • the QR code (SVG, ~200px, quiet zone). A QR must stay dark-on-light to scan, so put it on an explicit light surface in both themes;
    • a line: {toName} · {upiId} and the amount, large and tabular;
    • primary action: Open UPI app as an <a href={link}> styled as a button (no target="_blank"; custom-scheme links must navigate in place to trigger the OS app chooser);
    • secondary action: Record payment → closes the dialog and calls the existing openRecord(suggestion);
    • a one-line caption: "Scan with any UPI app, or open yours. Then record the payment here — Outlay can't see whether it went through."
  • The dialog never writes. "Record payment" is the only path to the existing sheet.

QR rendering

Add qrcode.react (client-only, renders <QRCodeSVG value=… />, no canvas, ~10 KB). Medium error-correction level (level="M"), which is what UPI QR codes in the wild use. The QR value is the identical upi://pay?… string.

Tests

  • Unit (src/lib/upi.test.ts): amount formatting from minor units (124000 → 1240.00, 5 → 0.05, 100000000 → 1000000.00), encoding of names with spaces/&, note truncation, exact query ordering.
  • Validator (member-schema.test.ts or alongside): accepts name@bank, 9876543210@ybl, Name.Surname@OKAXIS (lowercased); rejects name@, @bank, name bank@upi, name@b@nk; empty → undefined.
  • Integration: createMember/updateMember persist and clear upiId; getMembers returns it.
  • E2E (e2e/): the e2e fixture seeds one member per household, so /settle-up has no suggestions out of the box. The spec first adds a second settle-up member ("Carol") through the Members sheet, then sets a UPI ID on the seeded payer (Alice, who paid the three ₹100 expenses) — this yields a "Carol → Alice ₹150" suggestion.
